# RC11 offline startup evidence — pre-API failure slice

This is an incremental part of [Debug & QA Diagnostics Centre #85](https://github.com/DigiLogicTech/OnePane/issues/85), not a completed installer recovery or attestation system.

## What is implemented

- Windows service control-manager wrapper emits bounded **typed** events before the backend becomes healthy, including readiness failure and unexpected post-start exit. Health readiness now requires an HTTP **2xx**, rather than accepting 4xx errors.
- Windows backend records configuration, SQLite/service bootstrap, state lookup, listener startup intent and listener failure. The service explicitly passes the configured application root through a controlled process environment variable so configuration parsing failures can still leave evidence.
- Ubuntu backend uses `ONEPANE_STARTUP_EVIDENCE_ROOT=/var/lib/onepane` from the packaged and standalone systemd unit, including failures before config has loaded. Custom installations generated by `install-ubuntu.sh` point this variable to the installer-selected `ONEPANE_DATA_DIR`. The binary records the same typed bootstrap stages.
- **Legacy Windows EXE setup only** adds typed install, payload, service registration, readiness and rollback outcomes. These are not MSI transaction events. The current RC10/RC11 MSI is WiX-based: Windows Installer failures **before the service launches are not captured** by this slice and still require explicitly requested, locally stored MSI logs and separate consent/redaction.
- Evidence is written without the WebUI, API, SQLite, network access or model runtime. No raw error strings or stderr are imported into the diagnostic journal.

## Location and bounds

The journal is under `<persistent application root>/diagnostics/`, with separate allowlisted files `backend.jsonl`, `windows_service.jsonl` and `legacy_setup.jsonl`, each capped at **32 KiB** plus one **32 KiB** rotated `.1` file. Each event contains exactly schema, UTC timestamp, component, stage and outcome. No usernames, machine names, Project identifiers, model names, paths, host environment, command arguments, prompts, tokens, credentials, or exception messages are stored in these typed rows.

The directory must be private (0700 on POSIX); files are created with 0600 on POSIX. Symlinked diagnostics directories/files and existing publicly accessible POSIX diagnostics folders are refused. Windows permissions additionally depend on the provisioned ProgramData/data-root ACLs; the diagnostic journal does not magically secure an otherwise insecure parent folder. Writing evidence is **best effort** and cannot fail a normal installation or block service startup.

This does **not** scrub the separate pre-existing `onepane.log`, historical setup logs, Windows Installer logs or systemd journals. Treat those as potentially sensitive and do not automatically include them in support bundles.

## Inspect offline

When the backend API is unavailable, an operator with filesystem permission can run the installed **OnePane.Backend** binary without opening the server:

```powershell
& 'C:\Program Files\DigiLogic\OnePane\OnePane.Backend.exe' -startup-evidence-root 'D:\OnePane'
```

Example assumes `D:\OnePane` is the configured **application root**; verify its actual location first. The option only reads and parses fixed journal paths, validates the event fields, and prints a JSON array to local standard output. There is no network request, token access, service start or upload. Windows users must use the actual installed executable path (the legacy EXE installer may use another location).

Ubuntu:

```bash
sudo -u onepane /usr/bin/onepane -startup-evidence-root /var/lib/onepane
```

For custom non-Debian installations, use the configured `ONEPANE_DATA_DIR` and the correct binary path. If the directory doesn't exist, is inaccessible, or is unsafe, the command fails with a generic message rather than showing source paths or OS exceptions. Since the results reflect local files, they are *diagnostic hints*, not trusted proof of a particular execution or absence of prior failures.

## Gaps to retain on #85

- WiX/MSI transaction capture requires opt-in `msiexec /L*v` (raw log can contain sensitive public properties, custom paths and machine information); do **not** auto-package raw installer logs.
- No collection of Windows SCM event logs, old systemd journals, crashes that occur before the service wrapper runs, uncaught OS termination without recording, or host-wide temp files.
- Not yet embedded as an operator-reviewed source in the browser-generated consolidated QA ZIP. The API may be unavailable; avoid making the support ZIP require it.
- Real Windows MSI upgrade/reinstall, Linux service boot and disk-full/ACL faults still require physical operator verification. An absent journal means *not observed*, never that startup was successful.

**Release boundary:** RC10 remains the recovery baseline. No RC11 release until the first code audit, user vision interview/approval and second audit/approval gate #86.
