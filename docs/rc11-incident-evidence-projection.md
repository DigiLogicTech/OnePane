# RC11 — Bounded incident evidence review

A new **read-only** Project-scoped incident view ties an existing human-owned review case to its original TCP baseline drift notice, the first independently admitted historical TCP return-to-baseline receipt (when present), and at most eight already-recorded signed instrument **self-report** claims that identify the same **operator-declared** exact endpoint.

`GET /v1/projects/{projectID}/continuous-goals/{goalID}/incident-reviews/{reviewID}/evidence` is authenticated, **human-only**, and requires `project.read`. No input body, raw IP/port, signature, TLS certificate, credential, challenge, external network call, Task, case mutation, incident declaration or remediation can originate from this endpoint.

A later signed instrument claim is associated only when its immutable challenge, key, TLS pin, Project, Goal, source, canonical Workspace and declared target match the original approved TCP permit and a declaration that predated the original TCP attempt. Claims are bounded to a 15-minute historical window around the drift detection timestamp and returned as metadata, including `proof_class` explicitly describing a non-attested instrument self-report. Temporal proximity and matching operator-assigned endpoint are **not** independent device-identity, physical-vantage or sensor-accuracy proof.

The response explicitly returns `device_identity_verified=false`, `independent_vantage_verified=false`, `incident_confirmed=false`, `remediation_authorized=false`, and `endpoint_association=not_established` unless matching historical signed claims exist (in which case `historical_operator_declared_same_endpoint`). If missing, revoked or stale grants prevent the original source from being attributed historically, that association stays absent. The case and original alert remain open or reviewed independently; historical return-to-baseline never asserts current device health.

Source-level validation includes scoped HTTP tests rejecting Agents/anonymous/foreign access and showing no secrets or false positive, plus SQLite service integration checking that no synthetic claim is inferred from a TCP reachability notice. The full cryptographic accepted-claim path is separately covered by existing signed instrument regressions; end-to-end cross-source target fidelity, hardware-vantage identity and acceptance remain unproven. No release/packaging authority is added.

**Next gates:** signed instrument case fixture positive/negative linkage, longer historical lookup/endurance tests, user-reviewed reversible playbook boundaries and real physical Node measurement. Comprehensive UI/UX alignment remains last before QA build.

## Acceptance-time versus observation-time fence (2026-10-15)

Historical case correlation now requires **both** the server-accepted timestamp and the instrument's separately signed, **source-asserted observation timestamp** to fall inside the same bounded ±15-minute window around the original TCP drift. The existing challenge-issuance and accepted-before-now checks remain. A source may deliver a 90-second-delayed observation near an incident window edge; receipt time alone does not make the earlier observation contemporaneous. SQLite integration reconstructs a real approved challenge/key/signature/receipt chain, then advances a fake clock and a fake TCP dialer to a later separate drift: the delayed signed claim must not appear in that case. No observation timestamp is independently trusted as a physical clock or device-vantage attestation; matching still implies no incident confirmation or remediation authority.

## Bounded per-target historical retrieval (2026-10-15)

Additive schema migration `0095_goal_incident_measurement_lookup.sql` introduces a composite SQLite lookup index on `(project_id, goal_id, declared_target_id, source_id, accepted_at DESC)`, matching the existing historical review filters and the small time window. This avoids depending solely on the older goal-wide acceptance-time index when many unrelated instruments contribute receipts to the same Project. The signed proof rows remain immutable; the change neither discards audit history nor adds active monitoring, identity attestation or response permission. The existing real SQLite integration test also checks that the new index exists after a fresh schema migration. Real large-dataset WAL/disk and memory benchmarks remain a distinct acceptance gate; the index alone is not a measured performance guarantee.

## Operator-visible signed observation timing (2026-10-15)

The bounded metadata projection returns **both** `observed_at` (signed, instrument-declared and not an attested clock) and `accepted_at` (OnePane server acceptance) for each associated self-report. Operators can distinguish when the source *claims* it observed an endpoint from when OnePane accepted the claim; the response still omits network endpoints, signed bytes, raw evidence and unbounded history. SQLite integration asserts the exact two timestamps of an authentic accepted signed claim survive into the read-only case. Neither timestamp authenticates the physical device or independently establishes a security incident.

## Preserving signed evidence through additive schema upgrades (2026-10-15)

An extended SQLite integration regression starts with a populated current database containing an actual enrolled Ed25519 instrument key, original signed challenge and accepted self-report. It reconstructs the immediately preceding schema by dropping only index 0095 and its ledger entry, runs the real production `DB.Migrate` path, and verifies the rebuilt index, historical case association, unchanged original signing payload/public key/detached signature and independently verified signature. The production migration backup and data-preserving path are exercised, without installed Windows/Ubuntu testing; a real pre-existing customer database, disk benchmark and rollback from a failed migration are still separate release gates.

## Source disagreement metadata is not cross-sensor corroboration (2026-10-15)

The bounded human-only incident review projection now gives operators `signed_claim_consistency` (no claims, consistent unverified self-reports, or conflicting unverified self-reports) and `distinct_signing_keys`. A single software key may produce repeated, mutually contradictory valid signatures; the returned count is **enrolled software signing keys**, not verified hardware, independent sensor vantages or incident votes. All physical identity, independent vantage, incident confirmation and remediation-authority booleans remain false. The function processes at most eight already-selected metadata records without new outbound requests, database schema changes, model calls or background tasks. Pure unit cases cover zero claims, duplicate same-key claims, contradictory outcomes and multiple un-attested keys.

## Consistent read snapshot for historical incident reviews (2026-10-15)

The Project/tenant active check, human case record, original TCP drift receipt, later return-to-baseline evidence and at-most-eight signed instrument self-report rows now execute against a single read-only SQLite transaction. This prevents one HTTP response assembling different parts of an incident from separately committed database states when concurrent reviews, suspensions or revocations occur. The read transaction is rolled back on every early return and error, or committed on the complete path; it creates no Task, sensor call, network change or remediation authority. Existing real SQLite integration covers both the no-association early return (followed by new write admission) and the populated read and migration path. This is consistent *stored* evidence, not proof of current physical health or physical device identity.

## Signed contradictory report integration (2026-10-15)

SQLite admission now has a dedicated full-path regression for **one genuine enrolled Ed25519 signing key providing two opposing TCP-connect self-reports** through separate single-use challenges. Human incident evidence retains both authenticated source claims while explicitly showing `conflicting_unverified_self_reports` and `distinct_signing_keys=1`, with physical device identity, independent vantage, incident confirmation and remediation authority all false. The fixture also checks a delayed third report cannot be correlated to an unrelated later drift and that all three records survive additive migration 0095. Simulated TCP sockets and key signatures are controlled by the test; this is not a successful physical Node acceptance.
