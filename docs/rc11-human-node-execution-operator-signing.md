## Separate human Ed25519 signature for portable Node execution approvals

The human-only OnePane Project API issues a short-lived challenge-specific execution permit, with a separate revocation/inventory endpoint. Its JSON is not server-signed. An operator must obtain the original approved permit using a trusted authenticated session, keep it private, and run onepane-node-custody sign-execution-permit with --permit, --operator-private-key, --operator-principal-id and --output. That operation uses a separately enrolled protected operator Ed25519 signing key, signs the canonical original approval with a domain-separated v1 message, and writes a new exclusive owner-only transfer file.

The explicit onepane-node-custody probe-and-witness operation now requires --execution-permit pointing to this signed envelope AND --operator-public-key supplied over an independently trusted operator channel. It verifies that signature and rejects equality with the instrument and Node public signing keys. It then validates original Project, Goal, Workspace approval metadata, challenge SHA-256, declared target/TLS pin/source, Node identity and certificate, instrument key, short expiry and original trusted private endpoint plan before spending a nonce or opening any socket. No unsigned downgrade or implicit fallback is allowed.

This is an operator key signature, NOT a cryptographic server signature. The operator key must be enrolled separately; no evidence here cryptographically maps it to OnePane Workspace membership independently of the authenticated issuance record. Offline revocation after transfer remains ineffective until permit/challenge expiry; server-side review and proof acceptance must independently check live state. Protect human, Node and instrument private keys separately, and require Windows ACL review on real hardware. This does not attest physical sensor execution, network vantage or external device truth, nor permit automatic L5 incident/remediation decisions.
