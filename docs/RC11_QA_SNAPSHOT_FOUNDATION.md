# RC11 — Workspace QA diagnostic snapshot (foundation)

This is an **incremental, explicitly limited part** of [Debug & QA Diagnostics Centre #85](https://github.com/DigiLogicTech/OnePane/issues/85). It is not the final global Debug Centre or a replacement for system/installer/Node trace capture.

## Operator flow

1. Open the **Project → Development Workspace → Workspace Task queue**.
2. Expand **QA diagnostic snapshot (read-only, opt-in)**.
3. Choose **Review included data**. OnePane checks the current logged-in principal's `project.read` and `task.read` rights, resolves the exact Project and canonical Workspace and returns up to 50 recent scoped Task status summaries.
4. Inspect the shown JSON, excluded categories and status. **Generate QA ZIP** becomes available only after successful preview.
5. Optionally choose **Copy sanitized QA summary** to copy a short text report (build version/revision when format-valid, UTC time, Task-state counts and error-event totals). It does **not** copy Task names/objectives, IDs, source paths, prompts, raw traces or log payloads. If the browser blocks Clipboard access, the read-only text area is selected for manual copying. No automatic upload.
6. Choose **Generate QA ZIP**, then inspect the locally saved `onepane-workspace-qa-snapshot.zip` before deliberately attaching it to a bug report. OnePane does not automatically upload it to a server or vendor.

### API

- `GET /v1/qa/workspace-snapshot?workspace_id=<tenancy>&project_id=<id>&project_workspace_id=<canonical-id>` returns the allowlisted JSON preview.
- `POST /v1/qa/workspace-bundle` with JSON `{"workspace_id":"…","project_id":"…","project_workspace_id":"…"}` returns a small on-device ZIP; normal authenticated session **and CSRF protection** apply.

Both are denied when tenancy/Project/Workspace scope or permission is not valid. They use the existing scoped Task reader and scoped Worker/dependency projections; no raw journal, arbitrary SQL, Task completion, model prompt, source file or log payload is serialized.

### ZIP manifest

Contains exactly:
- `manifest.json`: schema version, created UTC, origin, excluded categories and SHA-256 digests.
- `snapshot.json`: sanitised Task IDs and opaque Task/Run refs, state/revision/update time, permitted latest Worker status/counters, hard dependency counts, and **up to 96 recent Task/Worker event ledger entries**. The event timeline includes only a fixed known event-type vocabulary, timestamp, severity, and SHA-256-derived Task/Run/event/trace/request references; it excludes event payloads, principal IDs, messages and unknown event types. No objective, raw continuation, execution inputs, failure text or tool output.
- `README.txt`: explicit limitations and sharing guidance.

Up to **50 Tasks and 96 timeline events** (sorted newest first); the ZIP is in-memory, maximum **128 KiB**, with fixed archive paths. It neither writes a temporary system log nor archives arbitrary folders. Source changes after preview may alter the fresh exported snapshot.

### What this version cannot diagnose

It can correlate existing Task/Worker event metadata but **cannot yet capture per-click UI actions, complete cross-component HTTP traces, MSI setup logs, system resource snapshots, raw Node diagnostics, interactive timeline filtering, operator-entered reproduction notes or time-limited verbose instrumentation. These remain open in #85. A missing Worker run is reported as no execution entry—not as proof that execution occurred or succeeded.

**Release gate:** Finish #85 plus [three-phase code audit → vision questions → second code review #86](https://github.com/DigiLogicTech/OnePane/issues/86) before RC11 packaging. Preserve RC10 as the recovery baseline.

## Opt-in browser incident capture (incremental #85 implementation)

The Development Workspace Task queue now also has **Browser incident capture**, separate from the Task/Worker ZIP. This is an in-memory session recorder controlled by the **user**, not always-on telemetry.

1. Expand **Browser incident capture** and select **Start capture**. Recording is **off by default** and starts only from that button. It continues across OnePane routes in this browser tab, even when the Workspace panel is no longer visible. It never automatically starts after refresh/restart.
2. Reproduce the problem and optionally press **Mark issue** to insert a timestamped bookmark. **Stop capture**, or allow the hard **10-minute expiry** to stop automatically. Capture can be cleared at any time.
3. Select **Review incident trace**. It shows a bounded, locally constructed JSON report with generic UI button/link/form activity, fixed route categories, API *subsystem buckets*, request method, response status and elapsed milliseconds, and counts of unhandled browser errors. **No exception messages, stack traces, raw API paths or parameters, bodies, text inputs, clipboard, chat or model output.**
4. Select **Download reviewed JSON**, which is available only after stopping and reviewing the exact report. A changed/restarted capture requires reviewing again. The downloaded `onepane-browser-incident.json` is created entirely by the browser; **OnePane never uploads the report or transmits it to a diagnostic backend**. Attach it manually together with the separate Workspace QA ZIP only if you choose.
5. **Clear capture** removes the in-memory events. Navigation between pages preserves the current capture, but browser refresh/restart clears it.

**Safety:** Capture expires after 600 seconds, retains only 120 recent events and discloses a count of events dropped if exceeded. Only same-origin `/v1/` request categories are observed, without paths, queries, headers, bodies or content. DOM listeners and the temporary browser fetch wrapper are removed when capture ends. The recorder does not change network requests, task permissions, local/cloud inference routing, agent tools, Workspace isolation or any backend policies.

**Limits:** A browser-side incident timeline is not end-to-end server tracing and does not include installer logs, Node/container journals, Agent Check offload telemetry, Windows service logs, or user-entered reproduction notes. Neither the new incident JSON nor the older scoped Workspace ZIP is the complete consolidated support bundle. Those remain mandatory work in #85.

## Local model Agent Check evidence (incremental #85)

A read-only **QA evidence** button is available in the Local Model **Agent Check** review dialog. Selecting it opens a permission-checked preview; the operator can then choose **Download reviewed JSON** to save `onepane-agent-check-qa.json` locally. No upload or model inference occurs merely from viewing diagnostics.

The endpoint is `GET /v1/qa/model-deployments/{deploymentID}/agent-check`. It authenticates the current user and enforces OnePane's existing `model.read`/managed-deployment authority before opening any evidence records. It does **not** enumerate other models or Nodes. Model deployments that belong to the Node-wide inventory continue to require the existing administrator authorization.

The report includes only:
- Opaque hashed deployment/session references (not the raw IDs).
- Actual stored model deployment status, reported residency state and last update time.
- Up to **10** latest testbed sessions, their known status (`active`, `completed` or `cancelled`), start/end timestamps and counts of *persisted successful* inference and synthetic tool-probe turns.
- **For newly observed failures after the RC11 schema upgrade:** the latest machine-coded stage and broad category, with observed timestamp. Categories include deadline/cancellation, missing resource, invalid response, persistence, runtime execution, or explicit session abort. They are generated from known code paths and error types, **not** by exporting arbitrary runtime messages. The report prefers the latest **non-abort** failure over the UI's later cleanup/abort event so cleanup cannot conceal a previously recorded failing inference stage. If the only evidence is an abort, it reports that explicitly. This is a selected observed stage, not a guaranteed root-cause diagnosis. Older sessions retain the `not_recorded_as_structured_evidence` state; no backfill guesses.
- Explicit limitations and whether older sessions were truncated.

**Important limits:** The Testbed schema stores full request/response JSON and arbitrary notes; the QA projector does not select them. The separate additive `model_agentcheck_failure_observations` table stores only fixed stage/category enums and timestamps; its contents cannot be edited/deleted. Not every error path has a persisted Testbed session: preflight failures before session creation and diagnostic-write failures may still lack evidence. A cancelled session is **not** proof of a particular inference error. A reported model residency value is *not* an independently measured CPU/GPU load or proof of model unload. Failed probes that never became persisted turns are not counted; absence of turn evidence is not success or failure evidence. No remote Node state, GPU telemetry, driver diagnostics, error text, installer log or raw model output is returned. Full correlation and redaction acceptance remain on Debug Centre issue #85.

This feature is separate from the authorised Workspace Task ZIP and the opt-in browser incident JSON. A consolidated support bundle is **not yet built**.

## Legacy Agent Check qualification privacy remediation (migration 0042)

Older OnePane manual Agent Check v2 qualification records could include raw exception strings under `evidence.errors`. Those messages may contain local paths, backend output or even sensitive string values. They are **not** needed to diagnose failures now that typed failure observations exist.

- **New failures:** manual qualification v3 stores only `infrastructure_error` and the fixed `inspect_structured_agentcheck_evidence` guidance. It does not write `error.Error()`; successful testbed completion also does **not** copy raw error arrays into a qualification report. It counts any typed failure observations and limits the result rather than silently marking a recovered but previously failing session fully passed.
- **Existing records:** additive migration `0042_redact_legacy_agentcheck_errors.sql` removes the known `$.evidence.errors` arrays from `model_spec_sheets.qualification_json` and removes the corresponding nested `$.qualification.evidence.errors` arrays from `model_identity_specs.qualification_json` for **manual Agent Check v2 only**. A fixed `redacted_on_upgrade` marker replaces the removed content. Model inventory, installation locations, admissions, testbed sessions, observed performance values and unrelated qualification documents remain intact.
- **No invented history:** migration 0042 does not synthesize failure categories for old records, change production admission decisions, or claim that all old probe errors can be classified. Structured failure observations from migration 0041 remain the preferred source of new evidence.

**Data-remanence limitation:** This migration removes sensitive values from live logical records; it does **not** erase old database backups, copies already exported, retained WAL frames, SQLite free pages or files elsewhere on disk. Historical backup retention and storage-level secure-erasure policy need separate review during the pre-release code/security audit. No blanket VACUUM or filesystem deletion is performed automatically, to protect existing installations.

This is a targeted data-privacy remediation, not final physical Windows/Ubuntu or installer validation.

## Admin-only Node control-plane diagnostics (incremental #85)

Open **Nodes → Manage node → QA evidence** to view the selected Node's persisted control-plane observations. The read-only route is `GET /v1/qa/nodes/{nodeID}/evidence` and reuses OnePane's existing **Node Administrator** check, not ordinary Workspace access. After viewing the plain-text report, use **Download reviewed JSON** to save `onepane-node-qa-evidence.json` locally. The report is never automatically uploaded.

The report deliberately includes only machine-typed metadata: a pseudonymous Node reference, recorded local/remote trust state and last-seen timestamp, capability manifest receipt/expiry timestamps and sequence (never the manifest contents), known pairing state, aggregated historical wake attempt results and aggregate remote-inference receipt statuses. Every query uses the exact administrator-selected registered Node ID. Missing manifests and unrecorded events show explicit unavailable states rather than fabricated success.

**Local service-manager observation (incremental):** For the **canonical local Node only**, an administrator opening QA Evidence now triggers one bounded, read-only check of the packaged OnePane service: `/usr/bin/systemctl show ... onepane.service` on Linux or the fixed `OnePane` Windows SCM query through System32 `sc.exe`. The server uses no shell, no user-provided service names, no privilege escalation, no remote execution or journal/log read, a **2-second deadline**, and an **at-most-4-KiB discarded-output buffer**. Only an allowlisted status (`running`, `stopped`, `starting`, `stopping`, `failed`, `paused`, `not_installed`) and the collection source/time are returned. If a query fails, times out or is unsupported, `operating_system_service_state` remains `not_collected` and the collection status indicates why.

**Operational caveat:** The service-manager result is **not** end-to-end OnePane application readiness, and even `running` does not establish healthy tasks, models, storage or dependencies. Node last-seen timestamps and historical inference receipts still do not establish current reachability. For **remote Nodes**, `operating_system_service_state` remains **`not_collected`**; no remote commands or privileged Node-agent operations occur. Local OS manager checks do not include logs, raw process arguments, driver diagnostics or GPU/CPU measurements. Installed Windows/Ubuntu acceptance testing and separately governed remote service health remain outstanding under #85.

Excluded: TLS keys and pairing codes/tokens/certificates, endpoint URLs, manifest payloads, wake targets, task IDs, remote request IDs, model inference outputs, error codes, log strings and raw service journals. This report is separate from the Workspace QA ZIP, browser incident trace and Agent Check JSON. Consolidated privacy-reviewed support-bundle packaging remains outstanding.

## Consolidated reviewed QA support ZIP (incremental #85)

Open **Project → Workspace → Tasks & AI development → Consolidated QA support ZIP**. The operator must explicitly **Review consolidated data** before the **Download reviewed support ZIP** button becomes available. The default bundle contains only a freshly authorised aggregate of the canonical Workspace's Task states and selected Task/Worker event-type counts. The operator may optionally select a *stopped/expired* browser incident capture, enter a model deployment ID for an authorised `model.read` Agent Check report, or enter a registered Node ID for the existing **Node Administrator** evidence report. Requested sources are never silently omitted if permission checks fail.

**Privacy design:** The browser constructs the ZIP entirely in local memory, using four separate **strict field-allowlist projections**. No raw server snapshot, Task IDs, Project/Workspace IDs, user names, free-form field values, model prompts/responses, source files, service logs, pairing credentials, process arguments, paths or request URLs are ever copied into the combined archive. The optional model/Node selector IDs are used only to make separately authorised API requests and are *not* exported. Browser events are only included after a stopped opt-in capture and cannot grow beyond 120. The bundle's five fixed possible file names are `manifest.json`, `workspace.json`, `browser.json`, `agent-check.json` and `node.json`. Missing optional files are simply absent when not selected.

**Preview and export contract:** The entire projected JSON is shown as plain text (not HTML). The operator reviews this exact representation before a browser-local ZIP is produced. Any changed source selection, changed browser recorder contents, changed preview, or more than **two minutes elapsed** invalidates the review and requires a new one. The ZIP uses an internal dependency-free, uncompressed STORE format with CRC32 and a hard **256-KiB** maximum size. The combined preview is capped at 192 KiB, and each archive member at 128 KiB. Browser data is **never uploaded or sent back to any QA endpoint**.

**Export-time authorization (incremental #85):** Export now performs a **fresh authenticated GET** for the same canonical Project Workspace and each explicitly selected Model or Node evidence source, using the current user session and the existing per-source permissions. A user whose role, session, model access or Node Administrator access was revoked after the preview can no longer export the prior review merely because it is less than two minutes old. Failed checks, a disconnected backend, an expired preview, changed selections or a discarded review all **fail closed** and require a new preview. The browser ignores the re-fetched documents: it exports **only the identical content the operator already reviewed**, with no new data silently entering the archive. The ZIP remains locally assembled and is never uploaded, but **export now requires the OnePane backend to be reachable** for reauthorization; offline export of a previously reviewed preview is deliberately not supported. No client-only recheck can eliminate the small race between the final server check and the user's actual download, nor revoke an archive the operator already downloaded.

**Evidence limits:** The Workspace component is a *summary* of state and event types, not the entire existing independently authorised Workspace Task ZIP; operator may still separately download its detailed bounded Task/Worker archive. Model and Node reports are limited to server-side typed machine observations and expressly do not prove external side effects or full GPU/OS health. The combined file is a **diagnostic aid**, not system attestation, and physical Windows/Ubuntu acceptance remains open. Installer errors, filtered service logs and redaction of database remnants remain separate tasks on #85/#28; the two formal #86 code reviews with the user-led vision realignment remain pre-release gates.

## Local backend readiness evidence (incremental #85)

The **Nodes → Manage node → QA evidence** action now includes an additional `backend_readiness` object for the **canonical local Node only**. Its caller already has to pass Node Administrator access controls. The report is generated on demand, never background-polled, and the other Node reports remain devoid of host backend information.

It checks only:
- A bounded **1.5-second** read-only SQLite `PingContext`, reported as `responding_read_only` or `unavailable`. This is not a disk-integrity or write-transaction guarantee.
- Actual recorded `schema_migrations` version numbers compared against the version identifiers embedded into the running OnePane binary. `recorded_versions_match_embedded` is a **coverage check only**; it is not a checksum comparison, schema correctness proof, or evidence that migrations ran successfully beyond their recorded state. Incomplete/unexpected versions are distinguished from unavailable reads.
- Presence of the canonical local Node record, using the server's internal Node ID and the database `local=1` registration flag. Remote Node IDs, even forged locally marked ones, cannot trigger this probe.
- Whether Tasks, Local AI, Vault and Federation service interfaces are **configured**, marked `configured_not_probed` or `not_configured`. These are dependency-wiring observations, not execution tests or access grants.

No raw DB records, schema SQL, database location, user/host identifiers, migration checksum, config value, Vault content, log line, executable argument or exception message are returned.

The independently reviewed **Consolidated QA support ZIP** also includes the bounded, field-projected readiness information in `node.json` if and only if optional Node evidence was explicitly selected and separately authorized. Its sanitiser accepts only the known schema and enums and never copies the raw server response.

**Failure mode limits:** The API itself must be serving requests to obtain this report. A OnePane backend that failed before binding HTTP cannot report its own startup failure through this endpoint. The OS service-manager observation can report whether the service is running, but cannot establish end-to-end control-plane health. For pre-listener bootstrap crashes, installer failures, log retention, and rollback events, a separately redacted, offline startup/installer diagnostics mechanism and physical Windows/Ubuntu acceptance remain required. No attempt is made to retrieve old service journals or leak environment data.

## Support ZIP integrity manifest (incremental #85)

The browser-generated **Consolidated QA support ZIP** now includes `integrity_algorithm: SHA-256`, `integrity_scope: extracted_utf8_member_bytes`, and a `member_sha256` map in `manifest.json`. Each key names one of the fixed, allowlisted member paths (`workspace.json`, `browser.json`, `agent-check.json`, `node.json`) actually selected for export. Each hex digest covers the precise newline-terminated UTF-8 JSON bytes inside that ZIP member. `manifest.json` itself is excluded to avoid recursive self-hashing.

The formatter recomputes hashes from reviewed, projected evidence and verifies them again while assembling the ZIP; changing a member after review without regenerating its digest causes export to fail. The archive remains fully local, STORE-only, at most **256 KiB** with an up-to-**192-KiB** reviewed preview, and requires the normal optional per-source authorization at review time. The implementation does not depend on HTTPS-only browser cryptography, so local/LAN WebUI operation can still produce integrity values without accessing a third-party service. NIST test vectors, multi-block/Unicode digests and verification against an independent SHA-256 implementation are included in CI.

**Integrity is not authenticity:** These hashes detect modifications to exported member bytes when checked against that same manifest. They are not a digital signature or a trusted-time record, and someone who can rewrite the entire archive can recompute all of its hashes. They also do not establish that underlying Task/model/Node observations are true or that no sensitive file exists elsewhere. Continue to review the included data before sharing.

## Central Debug & Diagnostics entry point (incremental #85)

OnePane now exposes **Settings → Debug & Diagnostics** and a **Debug** shortcut in the Logs drawer. The entry point uses the existing tab-scoped, **off-by-default** ten-minute browser incident recorder; there is not a second capture pipeline or elevated backend endpoint. Start, Mark issue, Stop and Clear operate on the same recorder used by the selected Workspace's browser incident controls. Moving between app routes does not stop an active capture; a browser reload clears it.

After stopping or expiring, choose **Review sanitised trace**. The centre projects source events through the same fixed allowlists used for consolidated QA support archives, shows the exact JSON locally, and allows **Download reviewed JSON** only while the underlying capture is unchanged and the review is at most two minutes old. Changes, a new capture, expiry or tampering with the preview invalidate export. The independent browser JSON export remains in-memory, capped at **64 KiB**, with no service upload, automatic persistence or raw log/credential fields. No free-form incident notes, raw API details, typed content or errors are captured.

**Scoped backend navigation:** Buttons direct the user to the existing Workspaces, Models, Nodes or Operations pages. The Workspace's existing canonical Project Workspace QA panel remains the place to review and generate the consolidated support ZIP and perform fresh Project/Model/Node authorisation. The Debug Centre does not automatically fetch or combine all accessible Projects, grant Node Admin privileges, bypass source permissions, change model routing or trigger autonomous tasks. This is a useful integrated entry point, **not yet** the full global correlator/filter/search interface described in #85.

If the backend failed before listener startup, the new Settings centre itself is necessarily unavailable. Use the offline typed startup journal and separate, opt-in MSI reader documented in [RC11_OFFLINE_STARTUP_EVIDENCE.md](RC11_OFFLINE_STARTUP_EVIDENCE.md).

**Still outstanding:** trace-level UI → API → Agent Worker → Tool Gateway → artifact correlation; timed backend Error/Normal/Verbose instrumentation with live resource overhead display; user-selected reproduction notes and attachments; offline integrated ZIP reimport; physical MSI/Ubuntu, multi-Node and browser responsive/theming QA. No RC11 package or RC10 overwrite has occurred.

## Scoped Task/Worker correlation from observed evidence (incremental #85)

The selected canonical Workspace **Development → QA diagnostic snapshot** section now includes **Correlate observed Task and Worker events**. A user must click to retrieve a fresh `GET /v1/qa/workspace-snapshot` with `cache: no-store` using the same authenticated, tenant/Project/canonical-Workspace checks as its existing QA preview. The frontend does not add a new service endpoint or alter identity or source permissions.

The pure correlation projector accepts only **schema v2** snapshots for `canonical_project_workspace`, limits input to the existing **96** event records and **50** Task records, and builds at most **48** groups. Event and severity types must come from a fixed list. The grouping keys use **opaque, format-validated** Task/trace/request/run references; raw Task/Run IDs, descriptions, event payloads, credentials, paths, host identities, prompts and free-form errors are never rendered.

A **shared trace** is displayed only where observed Task **and** Worker event rows have the same opaque Task and trace references. A **shared request** is labelled separately as weaker request-only evidence. Run-only and Task-only events can be shown without falsely declaring a cross-component trace. Events from different Tasks **never** link merely because they share a trace token. Severity filters (`All`, `Attention`, `Waiting`, `Information`) operate locally on the projected bounded view; observations are sorted by timestamp.

**Critical limits:** Browser API events do not currently carry a trusted backend trace reference. The view reports their link as **unavailable** rather than joining records by approximate time, route, status or model. Tool Gateway, lease, sandbox, provider, model and external verification links are similarly **not observed** by the Task/Worker timeline, and no "success" is inferred from a worker step or Task completion event. The new view does not copy reports, save traces, automatically send data or run a Task.

CI covers malicious canaries in event fields, unsupported event types, same trace across different Tasks, request-only versus trace links, denied/bad source schema, bounded events and groups, missing verification evidence, severity filtering, and navigation wiring. Physical Windows/Ubuntu UI and a complete tool-operation trace with independently verified side effects remain **release-blocking** acceptance work under #85.

## Structured QA reproduction note (incremental #85)

**Settings → Debug & Diagnostics → Reproduction report** now supports local, user-authored QA notes. A tester chooses a fixed subsystem and impact category, and enters a short title, reproduction steps, expected result and actual result. The form does not read source code, screenshots, arbitrary files, any API results, browser trace objects or secrets. Draft fields exist only on the currently mounted Settings view and are not persisted or sent over the network.

The user must click **Review my report** to see the **exact final plain text**. The program requires an explicit **privacy acknowledgement** after review; only then can **Copy reviewed report** or **Download reviewed text** be invoked. Edited fields, modified preview text or review age over **two minutes** invalidate the approval and require another review. Field lengths are capped at 120/1600/800/800 characters (title/steps/expected/actual), and the final UTF-8 report at **8 KiB**.

**Privacy distinction:** Unlike automatically projected browser, Model or Node diagnostics, **operator-entered notes cannot be guaranteed sanitised**. The output clearly states that it is *not automatically redacted* and warns against entering credentials, private Project data or personal information. Selected operator text is preserved faithfully for review; only unselected fields are excluded. The current browser capture, backend QA snapshot, consolidated support ZIP and offline logs are **never appended automatically**. Copy/download is a separate local action and does not upload the note.

This is not a full incident report with tool event attribution, screenshots or root-cause proof. Existing Debug Centre source links and Workspace-specific QA ZIPs remain independently authorised and must be reviewed separately. CI tests reject oversized fields, unsupported categories, stale/mutated/unapproved exports, and unintended inclusion of arbitrary source fields.

## Opt-in Node Admin backend HTTP diagnostic session (incremental #85)

**Settings → Debug & Diagnostics → Backend HTTP capture** now offers short-lived, administrator-controlled API diagnostics. Starting a session requires the existing `requireNodeOperator` (authenticated Node Admin) check; fetching or stopping its report independently repeats that check and requires **the exact originating principal and credential/session**. No new model, Project, Task or Node privileges are granted. Only one local server capture can be recording at a time; attempts to start another while active fail.

An explicit Start captures **60, 120 or 300 seconds** (backend permits 30–300 seconds). The server returns an unpredictable 192-bit ephemeral capture ID to the authenticated owner only. The browser stores it **in memory**, and the existing `apiRequest` client tags **only same-origin `/v1/` JSON requests** that it makes during this session. No other browser, agent, Node, background job or request without the matching capture header is observed. The server independently reauthenticates the owner credential and checks current Node Admin authority for each tagged request. Diagnostic control endpoints never tag themselves. This intentionally does not capture raw ad-hoc `fetch`, events arriving from services or unrelated users.

- **Normal** saves only fixed subsystem × HTTP outcome counters; **Verbose** additionally saves the newest 64 records containing a UTC timestamp, allowlisted subsystem, HTTP method, numeric status and capped elapsed milliseconds. The server never records full paths, URLs, query parameters, POST bodies, response content, raw headers, tokens, IP addresses, principal identities, exception text, prompts or model outputs.
- Captures **expire automatically** by the server's deadline, checked when observed or queried. The closed snapshot remains available to its original credential for at most **two minutes after stop/expiry**, then is lazily erased. No timers, background logging, filesystem persistence or external upload are introduced.
- The UI reads and reprojects the report through an independent fixed field allowlist and renders the result as text; it does not display the capture ID or accept unbounded server data. The button **Refresh capture status** is manual and checks Node Admin access again.
- `instrumentation_update_us` reports only measured counter/ring-update time inside the collector; it **does not** claim to cover reauthentication, writer interception, network delays, log volume, CPU/GPU usage or all instrumentation overhead.
- This is **HTTP envelope evidence only**. It does not imply model success, authorise Tasks, identify specific Workspace data, record Tool Gateway calls, establish causal UI → backend → worker chains, or verify outputs.
- Legacy MSI startup troubleshooting remains an offline, independently reviewed process. A backend crash before HTTP listener readiness cannot be diagnosed through this panel.

The API endpoints are `POST /v1/qa/api-capture/start`, `GET /v1/qa/api-capture`, and `POST /v1/qa/api-capture/stop`. They are intentionally not included in the consolidated Workspace QA ZIP, which has its own independent scope and review. The narrow time-bounded backend capture remains an incremental part of #85, not full debug level configuration across model/agent/worker runtimes.

Regression coverage includes unauthenticated and unauthorised access, credential/session isolation, denial of tagged outsider traffic, forged or absent capture IDs, missing JSON opt-in, no capture of diagnostic control endpoints, invalid durations, expiry/retention, verbose ring bounds, normal counts-only mode and raw request/response canaries.

## Task-associated model, Tool, operation and verification status (incremental #85)

The explicit canonical Workspace QA snapshot now includes **read-only, Task-associated execution status** from the persisted `inference_requests`, `tool_invocations`, `operations`, and `verifications` tables. Each source separately joins Tasks belonging to the **same authenticated tenant, selected Project, and canonical Workspace**, using only the newest 50 already-authorised Task identities. Each persisted execution row must additionally match the selected tenancy. Unavailable required tables or database errors make the requested snapshot fail closed; the API does **not** substitute a partial report from an unrelated workspace.

The response contains only SHA-256-derived, 24-hex-digit **opaque Task references**, fixed source labels, and bounded counts of **succeeded, failed, uncertain, pending, and unclassified** database states. It does not copy Task objectives, raw IDs, model/deployment/provider names, Tool identifiers, inputs/results, operation resources, verification evidence/results, database error strings, or file paths. Source counts greater than 65,535 are saturated and marked `capped`. The view includes up to 64 source-group rows, with an explicit `execution_sources_truncated` flag if further groups were omitted. It inherits the existing 64 KiB Workspace snapshot JSON and ZIP input ceiling, without raising support archive limits.

**Semantics:** A model request reported `succeeded` means its durable inference request state is `succeeded`, **not** that the model answer was correct. A Tool `succeeded` row means the persisted invocation reached that state, **not** that side effects were independently verified. An Operation `committed` is counted as succeeded and an independent verification record in `pass` is counted separately; the view does **not** infer that a particular Tool invocation caused a given verification. Cancelled and compensated terminal cases remain **unclassified** rather than falsely called successes or pending work. Unknown outcomes and interruptions are classified as uncertain. No untrusted free-form errors or raw event payloads are included.

The optional Workspace correlation UI displays these status groups **by the same scoped Task pseudonym**, in a separate section from the existing shared-trace/shared-request Task ↔ Worker timeline. **This is a Task-identity association, not an HTTP → model → Tool causal trace.** Browser/backend requests currently have no trusted shared capture trace, so no timing-based or guessed join is attempted. Severity filtering affects the timeline; the independent execution status groups remain visible and explicitly labelled unfiltered. The view is manual, read-only, and does not execute/retry Tasks or infer external action success.

Regression tests cover cross-Project and cross-tenant isolation, forged visible Task objects, missing tables, malicious source data, multiple outcome categories, cancelled/compensated status, count bounds and the 64-group coverage limit. Physical multi-Node/tool trace provenance, independently verified side effects and live Windows/Ubuntu QA remain outstanding.

## Three trusted provenance improvements — 2026-10-10 (RC11 #85)

1. **Operator-tagged HTTP Task creation → durable Task event.** During an explicitly started Node Admin backend capture, the server reauthenticates the browser credential and verifies its ephemeral capture token. For an exact `POST /v1/tasks` request, the server creates a 192-bit cryptographically random trace ID and places it in a *server-only request context*. The Task handler uses it **instead of any caller-provided `X-Trace-ID` header**. The existing Task event writer persists that trace with `task.created`. A successful 201 HTTP observation may include only its hashed `trace-<24-hex>` reference; neither raw trace nor user-provided header is echoed. A canonical Workspace's own authorised QA event timeline emits the same opaque hash. The Workspace reviewer may explicitly select **Include my Node Admin-owned HTTP capture**, which requires an independent, fresh Admin-authorised API read. Only a uniquely matching *Task creation* trace is linked. Unrelated API calls, failed create operations, untagged requests and later asynchronous Worker activity do **not** receive or inherit this trusted HTTP trace link. No timing-based correlation is used.

2. **Worker → Tool/Operation provenance.** The Worker QA projection independently rechecks persisted Task ownership against the chosen tenant, Project and canonical Workspace, then matches `agent_worker_steps.result_ref` to an `observations.id` whose exact `subject_ref` identifies the same-Task, same-Attempt, same-tenant `tool_invocations.id`. For mutation operations, journal result references join to `operations.id` with the same Task, Attempt and tenant. The read-only response contains hashed Task/Worker/Tool/Operation/Observation refs, known status enums, and a provenance label. These are **durable application associations**, not inferred HTTP causality. A Tool's result payload, input, resource path, adapter credentials and any free-form journal detail are never returned. The Worker tool-journal path currently persists the successful observation; failures without a durable result reference are **not invented** or silently treated as successful. At most 24 linked rows are shown with truncation indicated.

3. **Independent assurance chain.** Another scope-checked view reads the canonical Task's `verifications` plus matching `assurance_runs`; if a Worker run or operation is referenced, both must independently join the same Task and tenant before a linked reference is included. A **recorded assurance pass** requires persisted `verification.status=pass`, `assurance_run.status=passed`, an allowlisted SHA-256 digest recorded on the assurance run, achieved verification and assurance levels meeting the required V1–V5 level, and a verifier principal different from the correctly joined Worker principal. Invalid, absent or unrelated evidence is reported as incomplete or unlinked. No digest bytes, verifier identity, verification JSON, evidence payload, attestation or model text are exposed. **Even this complete recorded chain does not prove that an external side effect actually happened or that the verification procedure itself was correct.** A separate external probe would be needed for that claim. At most 24 records are included with explicit truncation.

All three projections are opt-in or scoped by an already-authorised canonical Workspace snapshot. There is no new unscoped endpoint, no automatic uploads, no Worker retry, no model-policy modification and no persistent verbose tracing. The existing 64-KiB QA snapshot and ZIP bounds remain. If any required backend source fails to load, the requested scoped snapshot fails closed. No released installer is affected; the release #86 audits and physical Ubuntu acceptance are still open.

## Durable asynchronous lineage and independently rechecked probe witnesses (incremental #85)

This increment closes the **identity bridge** across asynchronous Task execution without inventing distributed trace propagation. The already authorised canonical Workspace snapshot reads persisted Task → `task_attempts` → `agent_worker_runs` foreign-key relationships, independently rechecking Task tenancy, Project and canonical Workspace. It emits pseudonymous Task, Attempt and Worker references, typed states and a bounded step counter. This is a **durable database-identity link**, not a claim that HTTP trace headers crossed background Worker boundaries, nor evidence of successful inference or Tool execution. Only 24 most-recent rows are returned, with explicit truncation.

For verification, the snapshot now inspects the persisted **assurance evaluator's chosen observation references** from its recorded evaluation result, re-joins each observation to the selected Task's scoped verification/assurance run and re-hashes its **full persisted integrity envelope** using OnePane's existing `observation.IntegrityHash` verification logic. The operator sees only opaque Task, Verification and Observation references, the fixed direct/integration role, trust enum and boolean predicates for integrity validity, observation freshness relative to the Task Attempt and applicable Operation execution start, independently sourced observation, and a consistent recorded assurance result. A stored integration observation counts as a **corroborating integration record** only if it is independently sourced, fresh, integrity-valid and accompanied by a matching recorded V1–V5 assurance pass. No raw observation values, probe IDs, principal IDs, underlying hashes, inputs or result JSON are sent to the client.

**Important limit:** An independent observation is still an historical, persisted record. **No live external probe is launched by loading this QA panel**, and an integrity-valid historical observation cannot guarantee current external state. Actual post-action readback requires an approved independently executed probe appropriate to the Tool/adapter and resource, followed by provenance capture and repeat assurance. We intentionally do not grant the QA viewer authority to issue arbitrary network requests or mutate external systems. Missing/corrupt recorded observations result in no corroboration, never implicit success.

The new backend checks share the existing canonical Workspace authorisation, fixed 24-record caps, two-second scoped read deadlines (three seconds including rehash checks), and 64 KiB export ceiling. The UI rejects extra/unexpected references and computes conservative summaries from a secondary allowlist. Adversarial regression coverage includes forged Task membership, mismatched Attempt, cross-tenancy, stale readback, self-reported observation, tampered observation hash and explicit truncation. The mandatory #86 reviews and physical rootless Node acceptance remain open.
